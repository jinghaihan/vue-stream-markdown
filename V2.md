# Vue Stream Markdown 2.0 Design Plan

## Status

This document records the agreed direction for Vue Stream Markdown 2.0. It is a
design and migration plan, not a compatibility promise for the current 1.x API.

Version 1.1.0 remains the behavioral and visual baseline. Before starting the
2.0 migration, the rendering optimizations prepared for 1.1.0 should be tested
in the playground and released. The 2.0 implementation must preserve that user
experience unless a behavior change is intentional and documented.

## Goals

- Replace the mdast-based parser with Comark's compact document model and
  incremental parser.
- Keep Markmend's completion behavior, including project-specific streaming
  rules that do not belong in a general-purpose Markdown parser.
- Render Comark documents directly without converting them to mdast.
- Preserve the existing Vue renderer's UI, controls, progressive rendering,
  lazy loading, security behavior, and stable streaming updates.
- Make Comark parser options and plugins available to users.
- Simplify custom HTML and custom component rendering.
- Remove parser lifecycle APIs and implementation layers that become redundant.
- Retain or improve parser, rendering, memory, and bundle-size performance.

## Non-goals

- Maintaining source compatibility with the 1.x mdast API.
- Maintaining an mdast adapter or two AST formats.
- Replacing the renderer with `@comark/vue`.
- Forking Comark or maintaining a long-lived parser fork.
- Coalescing updates with latest-only async behavior.
- Reimplementing Comark's incremental source splitting in this repository.

## Why Comark

Comark's compact document model and stateful incremental parser fit streaming
Markdown better than the current mdast pipeline. Existing local benchmarks have
shown several-fold parsing improvements, with the largest documents showing the
greatest gains. Representative cold-parse results measured during the 2.0
investigation were approximately:

| Input  | Comark improvement over the current mdast parser |
| ------ | -----------------------------------------------: |
| Short  |                                            2.34x |
| Medium |                                            8.52x |
| Large  |                                           11.63x |

Representative streaming workloads ranged from approximately 4.20x to 11.76x
faster. These numbers are motivation rather than release targets and must be
rerun against the final 2.0 implementation.

Comark's parser is the main source of value. Its Vue renderer recursively maps
the document to VNodes but does not provide the styling, complex UI, stable
render boundaries, progressive behavior, or interaction model already provided
by Vue Stream Markdown. Version 2.0 will therefore use the Comark parser and
document model while retaining a purpose-built Vue renderer.

## Target architecture

```text
complete source from the caller
          |
          v
one long-lived serialized Comark parser per Markdown component
          |
          +-- Comark reuses the stable prefix
          |
          +-- streaming: Markmend completes the unstable tail through autoClose
          |   static:    Markmend returns the tail unchanged
          |
          +-- remaining user plugins and Comark default plugins
          |
          v
Comark MarkdownDocument
          |
          v
Vue Stream Markdown renderer
          |
          +-- stable top-level render boundaries
          +-- direct VNodes for simple tags
          +-- existing Vue components for complex/interactive tags
          +-- user-provided components by Comark tag
```

There is no Comark-to-mdast conversion step.

## Comark integration

### Version policy

- Start with exactly `comark: 0.6.2`.
- Do not use `^` or `~` in the dependency range.
- Keep a thin internal parser adapter so Comark API changes remain isolated.
- The adapter must not clone, normalize, or convert document nodes.
- Upgrade Comark deliberately after running the complete test and benchmark
  suites.

Comark is currently pre-1.0. The pinned package includes a small pnpm patch that
lets `autoClose` accept a synchronous function. The patch is removed after the
equivalent upstream API is available in a released Comark version.

### Parser lifetime

Each Markdown component owns one long-lived stateful parser. Every update passes
the complete raw Markdown source to that parser. Comark is responsible for
finding and reusing the stable prefix; Vue Stream Markdown will not pre-split the
document before calling it.

The parser instance must survive normal component updates. Recreating it would
discard Comark's incremental state and most of the expected performance gain.

### Ordered async updates

Parsing must use Comark's serialized parser API with a Vue `watch` and a
`shallowRef` for the most recently completed document.

- Parse every source update in order.
- Publish every successfully completed result in order.
- Keep displaying the previous document while the next parse is pending.
- Do not use `computedAsync` or latest-only cancellation.
- Do not discard intermediate updates merely because newer tokens arrived.

Latest-only behavior could leave the renderer unchanged indefinitely when token
arrival is faster than parsing. Serialized processing gives predictable output
and safely supports the stateful completion plugin.

### Parse errors

- A failed parse must not blank the rendered content.
- Retain the latest successfully parsed document.
- Emit an `error` event with the failure.
- Continue accepting later updates.

## Streaming completion

### Initial 2.0 implementation

Comark 0.6.2 only declares a boolean `autoClose` option. A small pnpm patch
extends it to accept a synchronous `(markdown: string) => string` function at
the existing auto-close stage. The initial integration will therefore:

1. Pass Markmend completion as Comark's `autoClose` function.
2. In streaming mode, complete the unstable tail supplied by Comark after
   incremental prefix reuse.
3. In static mode, return the tail unchanged.
4. Run user and default `pre` plugins after completion, matching Comark's
   existing pipeline.

This does not mean Vue Stream Markdown preprocesses the complete source itself.
The component still passes the complete source to Comark; Comark performs
incremental reuse, and the custom auto-close function operates on the remaining
unstable input.

### Future Comark integration

A first-class upstream custom auto-close function removes the need for the pnpm
patch. If Comark adds that API:

- Upgrade to the exact supported Comark version.
- Remove the pnpm patch.
- Keep Markmend completion at the same custom auto-close stage.

The public Vue Stream Markdown `completion` API should not change when this
internal migration happens.

### Public completion API

The Vue component will expose completion as either built-in options or a custom
synchronous function. A representative shape is:

```ts
interface CompletionContext {
  streaming: true
}

type CompletionFunction = (
  markdown: string,
  context: CompletionContext,
) => string

type Completion
  = | CompletionOptions
    | CompletionFunction
```

The completion function is only called in streaming mode. Static mode already
means "render the original Markdown without completion", so a separate global
`completion: false` mode is unnecessary.

`@markmend/core` remains independently usable and exports
`completeMarkdown(markdown, options)` for callers that only need completion.
Vue Stream Markdown does not need to re-export that standalone function.

## Document model and renderer

### Direct document consumption

The renderer consumes Comark's compact nodes directly:

```ts
type Node
  = string
    | [tag, attributes, ...children]
    | [null, attributes, comment]
```

There is no intermediate mdast, compatibility tree, or full-document node
cloning. Comark's stable top-level node references become the renderer's update
boundaries so unchanged blocks can avoid unnecessary work.

### Rendering strategy

- Render simple semantic tags directly as VNodes.
- Keep complex and interactive functionality in dedicated Vue components.
- Keep code highlighting, Mermaid, KaTeX, images, tables, HTML previews,
  overlays, controls, and error states behaviorally consistent with 1.1.0.
- Keep complex dependencies lazy where that improves startup cost.
- Mount modal and overlay behavior only when interaction requires it.
- Avoid maintaining both a legacy `.vue` renderer and a second equivalent
  direct renderer for the same simple node.

### Streaming state

Comark nodes do not need the current mdast-specific `node.loading` mutation.
Rendering behavior should use:

- the component's existing `streaming`/`static` mode;
- the active unstable top-level block where block-local behavior is required;
- injected renderer context for shared UI state.

This must reproduce the 1.1.0 interaction rules, including disabling unsafe or
misleading interactions while content is still streaming.

### Custom components

The mdast `nodeRenderers` API is replaced by a Comark-tag-based `components` API:

```ts
const components = {
  h1: CustomHeading,
  p: CustomParagraph,
  a: CustomLink,
  alert: CustomAlert,
}
```

- Node attributes are passed as component props.
- Node children are provided through the default slot.
- Custom components receive the original compact node through the reserved
  `node` prop.
- Shared renderer state is provided through Vue injection instead of repeating
  a large reactive prop object on every node.

Native HTML and Comark custom-component syntax use the same tag model. This
makes custom HTML support substantially simpler than parsing HTML into an mdast
node and reparsing it inside the renderer.

## Comark plugins and parser options

Comark's default plugins remain enabled. Version 2.0 should support the syntax
and document features they provide instead of disabling defaults to imitate the
1.x parser.

The public `parserOptions` API directly exposes Comark parser options, including
its `plugins` collection. A second top-level `plugins` prop is unnecessary.

`autoClose` is excluded from the public `parserOptions` type because completion
is owned by the separate `completion` API. This prevents two completion systems
from modifying the same input.

The package should export the relevant Comark document, node, parser-option, and
plugin types so users can write typed plugins and custom renderers.

## Security

The current `hardenOptions` API remains the security entry point. Existing URL
options should map to Comark's security behavior where possible:

- `defaultOrigin`
- `allowedLinkPrefixes`
- `allowedImagePrefixes`
- `allowedProtocols`
- `allowDataImages`

Version 2.0 may extend it with tag policy:

- `blockedTags`
- `allowedTags`

Comark's security plugin is not a default plugin, so Vue Stream Markdown must
register and configure it explicitly. It should handle dangerous tags,
attributes, and URL protocols before rendering. Vue-specific behavior such as
`errorComponent` remains in the renderer.

The migration must preserve existing blocked-link and blocked-image behavior,
including their error UI. Where early document sanitization would remove
information required by that UI, the renderer boundary must retain enough
metadata to reproduce the current result safely.

## Public API changes

Version 2.0 intentionally removes the mdast compatibility surface.

### Removed

- `mdastOptions`
- `getMarkdownParser()` and its mdast parser instance
- `getParsedNodes()` and mdast node types
- `nodeRenderers`
- `normalize`
- `preprocess`
- `preprocessOptions`
- `preprocessSteps`
- `postnormalize`
- `postprocess`
- `parseMarkdownIntoBlocks`
- mdast and micromark extension types re-exported by the package

### Added or replaced

- `parserOptions`: Comark-native options and plugins, excluding `autoClose`
- `components`: renderers keyed by Comark/native tag
- `completion`: built-in completion options or a custom completion function
- `getDocument()`: returns the latest successfully parsed Comark
  `MarkdownDocument`
- Comark document, node, option, and plugin type exports

`getDocument()` returns the last completed document while another parse is in
progress. It never exposes a temporary partially mutated document.

## Package changes

### `@markmend/core`

Keep it as a focused, parser-independent Markdown completion package:

- Export `completeMarkdown()`.
- Keep completion options and context types.
- Keep the completion implementation synchronous.
- Keep individual completion steps internal unless a concrete standalone API
  requirement appears.
- Fold only required source normalization into completion.
- Remove parser orchestration and source-block splitting.
- Remove the `marked` dependency if it is no longer required by completion.

The internal implementation currently named `preprocess` should become
`completeMarkdown` because preprocessing is no longer a public lifecycle stage.

### `@markmend/ast`

Remove this package in 2.0. Its responsibilities are replaced as follows:

| Current responsibility          | 2.0 owner                              |
| ------------------------------- | -------------------------------------- |
| mdast parsing                   | Comark                                 |
| source block splitting          | Comark incremental parser              |
| AST cache and reuse             | Comark incremental parser              |
| footnote/document transforms    | Comark plugins                         |
| position removal                | Not applicable to compact Comark nodes |
| streaming loading-node mutation | Renderer streaming context             |

## Migration phases

### Phase 0: freeze the 1.1.0 baseline

- Verify the optimized renderer in the playground and representative apps.
- Release 1.1.0.
- Record visual behavior, DOM stability, tests, and benchmark baselines.

### Phase 1: introduce the Comark engine in parallel

- Add exact `comark: 0.6.2` dependency metadata.
- Add the thin internal parser adapter.
- Create one serialized parser per test fixture/component owner.
- Pass Markmend completion through the patched custom auto-close option.
- Add document snapshots, plugin-order tests, parser benchmarks, and error tests.
- Do not convert Comark documents to mdast to reuse the old renderer.

### Phase 2: build the direct renderer

- Implement stable top-level document boundaries.
- Render text and simple tags directly.
- Establish the `components` contract and injected renderer context.
- Cover native HTML and custom component tags.

### Phase 3: migrate complex renderers

- Code blocks and syntax highlighting
- Links and images
- Tables
- KaTeX and inline math
- Mermaid and HTML previews
- Footnotes, alerts, controls, overlays, and errors

Each migration should compare DOM, styling, interaction, and streaming behavior
against the 1.1.0 baseline.

### Phase 4: switch the public component

- Connect `content` and `mode` to the serialized parser.
- Publish completed documents in order.
- Expose `parserOptions`, `components`, `completion`, and `getDocument()`.
- Add SSR and hydration coverage.
- Update documentation and examples to Comark-native concepts.

### Phase 5: remove the old stack

- Delete the old mdast parser and renderer path.
- Delete the old source-block cache and splitter.
- Delete obsolete parser lifecycle APIs and types.
- Remove `@markmend/ast` and unused mdast/micromark/marked dependencies.
- Verify that no compatibility layer or duplicate renderer remains.

### Phase 6: release validation

- Run correctness, type, SSR, browser, and platform test suites.
- Rerun parser, completion, rendering, memory, and bundle benchmarks.
- Test real streaming output in the playground.
- Publish a breaking-change migration guide.

## Test plan

### Correctness

- Complete/static Markdown corpus.
- Every prefix of representative streaming Markdown samples.
- GFM, frontmatter, tables, task lists, footnotes, math, HTML, and custom tags.
- All Markmend completion cases, including deliberately non-general rules.
- The custom auto-close function runs before user and default `pre` plugins.
- Security policies for tags, attributes, links, images, and protocols.

### Rendering and interaction

- Stable DOM identity for unchanged top-level blocks.
- No full-document flash when streaming becomes static.
- No missing styles from VNode renderer source files.
- Code, Mermaid, KaTeX, image, table, modal, fullscreen, copy, and preview flows.
- Link and image loading/disabled states during streaming.
- LTR/RTL behavior and accessibility attributes.
- Custom component props, slots, raw node access, and injected context.

### Async and failures

- Rapid token arrival preserves update order.
- Slow parses do not produce latest-only starvation.
- A rejected parse retains the last document and emits an error.
- Parsing recovers on the next valid update.
- Component unmount does not produce async teardown errors.
- Multiple Markdown components do not share parser or completion state.

### SSR and types

- Server rendering and hydration produce compatible output.
- Public Comark types work without users installing undeclared peer packages.
- Removed mdast APIs fail clearly in migration/type tests.

## Benchmark plan

Use identical documents and identical token chunk boundaries for every parser.
Keep completion-only, parser-only, and full-render measurements separate.

### Completion

- Markmend completion
- Comark built-in auto-close
- Streamdown/Remend completion

### Parsing

- Cold parse for short, medium, and large documents
- Growing single paragraph
- Token-sized appends
- Large stable prefix with a changing tail
- Appended blocks
- Middle edits

### Rendering

- Initial prose render
- Repeated prose appends
- Initial code-document render
- Repeated code-document appends
- Short growing code block
- Large growing code block
- Streaming-to-static transition

### Resource usage

- Retained document memory
- Peak memory during long streams
- Browser bundle size
- Initial dependency-loading cost

Compare Vue Stream Markdown 2.0 primarily with Comark and Streamdown under the
same workloads. Parser-only results must not be presented as full-render wins.

## Risks and mitigations

| Risk                                                             | Mitigation                                                                                          |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Comark 0.x API or plugin-order changes                           | Pin 0.6.2, isolate it behind a thin adapter, and test ordering explicitly                           |
| The temporary `pre` hook stops matching auto-close semantics     | Upgrade only deliberately; adopt a custom auto-close hook when Comark provides one                  |
| Grammar differences change rendered output                       | Prefix corpus, document snapshots, DOM comparisons, and documented intentional changes              |
| Ordered async parsing accumulates a queue                        | Retain serialized correctness first; measure real token rates before considering bounded scheduling |
| Stable document references do not automatically prevent Vue work | Use top-level render boundaries and DOM identity tests                                              |
| Security sanitization changes existing error UI                  | Test current link/image behavior and preserve required safe metadata                                |
| Custom plugins create unsupported tags                           | Resolve through `components`, native tags, or an explicit safe fallback                             |
| 1.x renderer behavior is lost during the rewrite                 | Treat released 1.1.0 as the visual and interaction baseline                                         |

## Release acceptance criteria

Version 2.0 is ready when:

- The renderer consumes Comark documents directly with no mdast conversion.
- Streaming completion retains the project-specific 1.1.0 behavior.
- Every source update is parsed and published in order.
- Unchanged content remains visually and structurally stable during streaming.
- Existing complex UI features behave consistently with 1.1.0.
- Custom Comark plugins, HTML tags, and Vue components work through the public
  APIs.
- Security defaults are at least as safe as 1.1.0.
- Parser performance retains a substantial advantage over the old mdast stack.
- Full rendering performance is not materially worse than 1.1.0 or Streamdown
  in representative streaming workloads.
- The old mdast packages, APIs, dependencies, and duplicate renderer paths are
  removed.
- The migration guide lists every breaking API replacement.
